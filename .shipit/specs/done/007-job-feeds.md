# 007 · Job feeds

**Status:** done · **Built:** 2026-09-05 → 2026-09-25 · **Verify:** `./verify feeds` · **Plan:** backend 002 (local, not in git)

## Why
Job boards and the agency's own public page need the list of open positions as a file they can
fetch, not as an API call per post. The agency wants every published post to appear in an XML and a
JSON feed under a stable address, without the feed slowing down or breaking the panel the
recruiters use.

## What it promises
- Every organization has two feed files, `{organizationId}/jobs.xml` and `{organizationId}/jobs.json`,
  in the `jobs-feed` bucket.
- A feed contains only the organization's `Published` posts; publishing, closing, archiving and
  editing a post change the next generated file.
- Each item carries the post's fields and an `applyUrl` built as `Application:FeedUrl` + `/` +
  post slug, so links point at the public job board.
- An organization with no published posts gets an empty, valid feed.
- Feeds are regenerated in the background: a scheduler queues one task per organization every
  30 seconds; a generator picks pending tasks every 120 seconds. A failing task is retried and marked
  `FAILED` after 3 attempts; a duplicate task id is ignored.
- Anyone can download a feed at `GET /p/{slug}/jobs.xml` or `/p/{slug}/jobs.json` (anonymous, not in
  OpenAPI); the public board gets the same files through the internal API.
- Only the worker host schedules and generates; adding API nodes does not multiply schedulers.

  `tests/HrAgencySystem.IntegrationTests.Persistence/Feeds`.

## Out of scope for this feature
- Board-specific formats (each job board's own XML schema) - one generic XML and one JSON (not yet).
- Pushing feeds to boards: boards pull the file (not yet).
- Feeds that react instantly to a change; up to two scheduler/generator cycles of delay is accepted (not decided).
- The panel never reads feeds (not ever: the feed has its own read model on purpose).

## Decisions
- Feed read model is a relational table filled by an EF projection and read with Dapper, generated by
  its own worker host: [ADR-0009](../../../docs/adr/0009-feeds-own-read-model-and-worker.md).
- The table is the whole contract: `Feeds` references neither `Recruitment` nor its events;
  `Recruitment` references `Feeds` only to fill the row: [ADR-0006](../../../docs/adr/0006-contracts-and-shared-kernel-ports.md).
- One process, many hosts only where they earn it - the worker earns it by owning the timers: [ADR-0001](../../../docs/adr/0001-modular-monolith.md).
- Projection methods are named `From`/`Update`, not `Create`/`Apply`: Marten refuses a document type
  with conventional methods inside an EF projection (plan 002 notes).
- No separate feed repository: `IJobFeedReader` already is the port, so it queries the table directly
  (plan 002 notes).
- A span per feed generation, so each SQL/S3 call is not a root trace: [ADR-0020](../../../docs/adr/0020-observability-via-collector.md).

## Notes from reconstruction
- Until plan 002 the feed was generated from `JobPostProjection`, the projection the panel reads;
  the plan's goal was to stop that coupling.
- The plan proposed a character test comparing generated files before and after; it became unit
  tests of the serializers instead, because `FeedUrl` is not set in the `Testing` environment.
- Every organization counts as "active" for the scheduler - there is no inactive organization yet,
  so an agency with no posts still gets a task every 30 seconds.
